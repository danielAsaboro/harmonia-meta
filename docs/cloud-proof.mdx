---
title: "How to capture deployment evidence"
description: "Capture proof of Meta Model API calls, workspace memory, Cloud Run, Firestore, Pub/Sub, and correlated execution."
---

This guide produces the evidence required to say that Harmonia ran end to end on Meta models. A successful local build or emulator run is not deployment evidence.

## Before recording

Use one dedicated Google Cloud project and one selected region, deploy both Cloud Run services with a real `model-api-key` secret, and complete one real authorized Harmonia job. Use a fresh job identifier that can be followed across every surface.

Prepare browser tabs for:

1. the signed-in Harmonia dashboard at its `run.app` URL;
2. Cloud Run services and revisions for `harmonia-web` and `harmonia-agent`;
3. the Meta developer dashboard usage view for the same time window;
4. the workspace's Firestore `memory_facts` collection showing a write from a verified outcome and a later retrieval in the same workspace/brand scope;
5. Pub/Sub delivery metrics for `harmonia-stages-agent-push`;
6. the workspace-scoped Firestore job, events, approval, receipt, verification, and usage records;
7. Cloud Trace or the telemetry backend filtered to the job's trace ID.

Redact customer content and account identifiers before recording. Do not open raw configuration or credential views.

## Capture a resumable asynchronous run

Create a job from an authorized source and show its job ID. Let at least one Pub/Sub-driven stage complete, then display the persisted Firestore stage and event timestamp. Restart the private worker revision or allow a safe redelivery, and show the same job resuming from durable state without creating a duplicate external receipt.

The proof is the correlation among the job ID, Pub/Sub delivery, Firestore state, Muse Spark usage records, and idempotent receipt, not narration alone.

## Capture cross-session memory

Complete a job through approval, independent verification, and learn. Show that workspace memory receives only an eligible fact such as an operator decision or verified outcome under the job's workspace and brand scope.

Start a separate later job in the same workspace and show its retrieval of that fact. Then show a different workspace producing no retrieval for the same query. If the two jobs have not actually been separated by weeks, describe the architecture as week-capable; do not claim elapsed-time evidence that was not captured.

## Capture the security boundary

Show the selected Cloud Run region, Firestore location, media bucket location, and Pub/Sub message-storage policy. State plainly that prompts and media go to Meta Model API outside that region. Show the two service identities and their distinct roles, the human approval boundary, and a metadata-only trace whose attributes contain no prompt, transcript, draft, or media content.

## Completion criteria

The evidence is complete only when it visibly includes:

- a working `run.app` URL;
- both Cloud Run services and their revisions;
- usage records for real Muse Spark, Muse Voice Transcribe, and (if approved) Muse Image calls;
- one workspace memory write and a later scoped retrieval;
- Pub/Sub activity and durable Firestore state for the same job;
- one approval receipt and independently verified outcome;
- one correlated metadata-only trace.

Store full-resolution screenshots, command output, job IDs, trace IDs, revision names, and timestamps under the private evidence directory. Until those artifacts exist, authenticated execution remains unverified.
